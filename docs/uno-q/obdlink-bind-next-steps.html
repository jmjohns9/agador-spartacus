Connect the bridge to the OBDLink

Tattlestone ↔ Arduino UNO Q ↔ OBDLink MX · next steps after the 2026-10-22 diagnosis · PR #12 (merged)

What's going on

The Wi-Fi side works: the app reaches the bridge on 192.168.1.33:35000. The bridge then tries to open /dev/rfcomm0, the Bluetooth serial link to the OBDLink, and that link doesn't exist yet. Every attempt in today's log ends with:

BRIDGE ERROR: cannot open /dev/rfcomm0: No such file or directory

/dev/rfcomm0 only appears after you pair the board with the OBDLink and run rfcomm bind. That's the main job below.

The app used to hide this reason behind "No response to ATZ/ATI". That's fixed in main (commit 9d91b7a, PR #12): the app now shows the bridge's own reason.

1 Check you're on the right build Mac

Every build reports version 1.0.0, so the version number won't tell you which code you're running. Check the git commit instead: open Tattlestone, go to Settings, and scroll down to About.

If it shows another branch, an older build, or Development build, rebuild from main:

The build prints a line like build-info: 1a2b3c4 (main). Quit and reopen Tattlestone so it loads the new build.

If the Build row ends in · uncommitted changes, the app was built from edited files that weren't committed, so it may not match any commit on GitHub. Commit (or discard) the changes and rebuild.

2 Check the new error message Mac

Before binding anything, confirm the app now explains the failure.

  1. Open Tattlestone, then go to Connection, then Network.
  2. Enter 192.168.1.33, port 35000, and click Connect.
Expected banner: The bridge can't reach the OBD adapter: cannot open /dev/rfcomm0: No such file or directory [BRIDGE ERROR]. The session log shows Connection failed: … and no "No response to ATZ/ATI" lines.

3 Get the truck and adapter ready Truck · Mac

  1. Plug the OBDLink MX into the Silverado's OBD port (under the dash, left of the steering column).
  2. Turn the ignition on. The engine doesn't need to run.
  3. On the Mac, disconnect from the adapter: System Settings → Bluetooth → OBDLinkMX… → ⓘ → Disconnect. The OBDLink accepts only one Bluetooth host at a time, so if the Mac (or a phone app) is holding it, the board can't connect.
  4. If your adapter has a pairing button, press it just before step 4. It stays discoverable for a few minutes.
  5. The UNO Q must be within Bluetooth range of the truck: a few metres, with no thick walls in between.

4 Pair the board with the OBDLink UNO Q

SSH in from the Mac:

ssh arduino@192.168.1.33

Start the Bluetooth tool:

bluetoothctl

At the [bluetooth]# prompt, type these one at a time:

power on
agent on
default-agent
scan on

Wait until a line like this appears (it can take 10–30 s):

[NEW] Device 00:04:3E:12:34:56 OBDLinkMX13659

The part after Device is the adapter's MAC address. Yours will differ from this example. Write it down, then type the commands below using your own MAC:

scan off
pair 00:04:3E:12:34:56
trust 00:04:3E:12:34:56
quit
  • If asked for a PIN or passkey, enter 1234. If that's rejected, try 0000.
  • If asked "Authorize service?" or to confirm a passkey, type yes.
  • trust lets the board reconnect later without asking again.
Done when you see Pairing successful and trust succeeded.
Don't type angle brackets like <MAC> anywhere. Bash reads < as "read from a file", which is what caused the earlier -bash: OBDLink-MAC: No such file or directory error.

5 Save the MAC in a variable UNO Q

Still on the board. This finds the paired OBDLink and stores its MAC, so you don't have to retype it:

MAC=$(bluetoothctl devices | grep -i obdlink | awk '{print $2}' | head -1)
echo "OBDLink MAC: $MAC"
Done when it prints a MAC like 00:04:3E:12:34:56. If it prints nothing, step 4 didn't find the adapter: see Troubleshooting.

Optional: check which RFCOMM channel the adapter uses (it's almost always 1):

sdptool browse "$MAC" | grep -i -A6 "serial port" | grep -i channel

If this prints Channel: 1 or errors with "Failed to connect to SDP server", use channel 1. If it shows another number, use that number in place of 1 in steps 6 and 9.

6 Create /dev/rfcomm0 UNO Q

sudo rfcomm bind 0 "$MAC" 1
ls -l /dev/rfcomm0
rfcomm -a
Done when ls shows something like crw-rw---- 1 root dialout … /dev/rfcomm0 and rfcomm -a shows rfcomm0: 00:04:3E:… channel 1 clean.

bind doesn't connect yet. It only reserves the device. The Bluetooth link starts when the bridge opens /dev/rfcomm0, which happens when the app connects. The bridge service is in the dialout group, so it can open the device.

7 Test the full path with nc UNO Q + Mac

On the board, watch the bridge log (leave it running):

journalctl -u tattlestone-bridge -f

In a new Mac terminal, send a reset, an ID request and an RPM request:

printf 'ATZ\r' | nc -w 4 192.168.1.33 35000; echo
printf 'ATI\r010C\r' | nc -w 6 192.168.1.33 35000; echo
Expected: an ELM327 v1.x banner, then a line starting 41 0C (RPM data) or NO DATA with the engine off, each followed by >. The journal shows Client … connected and no Cannot open.
The first connect can take a few seconds while Bluetooth links up. If the first command comes back empty, run it again.

8 Connect from Tattlestone Mac

  1. Connection → Network → 192.168.1.33 : 35000 → Connect.
  2. Watch for Adapter responded to ATZ, then Initialization complete. Protocol: SAE J1850 VPW (the 2004 Silverado's protocol).
  3. Open the live dashboard and check RPM and coolant temperature update.
  4. Export the session log (it saves next to the earlier logs in ~/Tattlestone).

9 Keep the bind across reboots UNO Q

rfcomm bind is lost when the board restarts. This systemd unit redoes it at boot, before the bridge starts. Run it in the same SSH session as step 5 so $MAC is still set (check with echo $MAC):

sudo tee /etc/systemd/system/tattlestone-rfcomm.service >/dev/null <<EOF
[Unit]
Description=Tattlestone: bind /dev/rfcomm0 to the OBDLink
After=bluetooth.service
Requires=bluetooth.service
Before=tattlestone-bridge.service

[Service]
Type=oneshot
RemainAfterExit=yes
ExecStart=/usr/bin/rfcomm bind 0 $MAC 1
ExecStop=/usr/bin/rfcomm release 0

[Install]
WantedBy=multi-user.target
EOF
sudo rfcomm release 0
sudo systemctl daemon-reload
sudo systemctl enable --now tattlestone-rfcomm
systemctl status tattlestone-rfcomm --no-pager
ls -l /dev/rfcomm0
Done when the status shows active (exited) and /dev/rfcomm0 exists. Then test with sudo reboot, wait a minute, and repeat step 7.
Check the unit has the real MAC: grep ExecStart /etc/systemd/system/tattlestone-rfcomm.service. If it reads bind 0 1 (blank MAC), $MAC was empty. Redo step 5, then this step.

10 Keep the board's bridge in sync with main Mac → UNO Q

PR #12 is merged, so main holds the same bridge the board runs. If you change the bridge later, copy from main and restart the service:

cd ~/Tattlestone/agador-spartacus
git checkout main
git pull
scp files/firmware/uno-q-bridge/* arduino@192.168.1.33:~/uno-q-bridge/
ssh arduino@192.168.1.33 'sudo systemctl restart tattlestone-bridge'
Don't copy from older branches such as docs/github-redesign. Their bridge doesn't have the BRIDGE ERROR message, the systemd units or the tests.
