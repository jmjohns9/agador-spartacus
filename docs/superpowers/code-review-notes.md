| `files/src/main/main.ts` connect / disconnect lifecycle | Async connect chains were not tied to the session that started them. A serial attempt that was disconnected or replaced later reported `error` over the running simulator, and the serial port's own `close` event (fired when we release the port after a failed attempt) overwrote the `error` with `disconnected`, so the failure reason never showed. | fixed (fix(main) commit 621d39e) |

| `files/src/renderer/components/ui/containers.tsx` `Card`, `files/src/renderer/components/ui/Metric.tsx` `Metric` (both set `overflow: 'hidden'`) | `ScrollPane` (`components/ui/containers.tsx`) is itself a `display:flex; flexDirection:'column'; overflowY:'auto'` container, so its direct children are flex items. Per the flexbox spec, a flex item's automatic minimum size is `auto` (content-based) *unless* the item's own `overflow` is not `visible`, in which case its automatic min-height is `0`. Because `Card` and `Metric` both set `overflow:'hidden'`, any `Card`/`Metric` used as a **direct** child of `ScrollPane` (not nested inside a `Grid`, which sizes its own rows independently) can be squashed by the flexbox shrink algorithm to less than its content height — down to a sliver — instead of the page ever growing tall enough to scroll. Reproduced via CDP (`getBoundingClientRect` / `scrollHeight` vs `clientHeight`) at the app's default 1400×900 window on **already-shipped, already-swept screens**: on `ParasiteScreen` a `Card` wrapping an `EmptyState` (122px of real content) rendered at 46.5px tall with the rest silently clipped by the card's own `overflow:hidden`; on both `HealthScreen` and `DTCScreen`, `ScrollPane.scrollHeight === ScrollPane.clientHeight` (no overflow at all — scrolling never engages even though the pages clearly hold more than 900px of content, because some `Card`s are being crushed instead of the pane overflowing). Confirmed pre-existing, not introduced by the Parasitic Draw sweep (Task 9), since it reproduces identically on `HealthScreen`/`DTCScreen`, which this task only read for reference and did not modify. Repro: `npm run build && electron . --remote-debugging-port=<port> --user-data-dir=<tmp>` with `NODE_ENV=production`, open any content-dense screen, and compare a `ScrollPane`'s `scrollHeight`/`clientHeight` via `Runtime.evaluate`. | fixed (fix(ui) flexShrink commit) |
| `files/src/renderer/screens/TransmissionScreen.tsx` `GearIndicator` / `TransmissionScreen`, `files/src/core/pidCatalog.ts` PID `01A4` entry | PID `01A4`'s `decode` returns a raw enum byte (0=Park…6=4th) and its `format` turns that into words (`'Park'`, `'1st'`, …), but `TransmissionScreen` reads it with the raw `usePID('01A4')` helper — it never calls `fmt('01A4', …)` — so the `gear` value is always a bare number (or `'—'` before the first reading), never a letter. `GearIndicator` and the gear-ratio reference table both compare that value against the literal strings `'P'/'R'/'N'/'D'/'3'/'2'/'1'` (or `'1st'/'2nd'/…`), which can never equal a number — no capsule ever highlights and the big gear readout never shows a real gear, regardless of what the TCM reports. Confirmed pre-existing: the pre-redesign `GearIndicator` used the identical `label === g` comparison against the same raw, un-formatted `usePID('01A4')` value, so this reproduces before and after Task 10's restyle — not introduced by the sweep. Repro: `npm run build && electron . --remote-debugging-port=<port> --user-data-dir=<tmp>` with `NODE_ENV=production`, Launch Emulator, open Transmission — no capsule ever turns accent-colored and the readout under it stays `—`/a bare number; `AllPIDsScreen` shows the same raw, unformatted value for PID `01A4`. | open |
